# Porto Sparkle Automatic Update Specification

Status: implemented; v1.0.2 bridge release verified; end-to-end update acceptance pending

Last updated: 2026-09-17

## 1. Decision

Porto will use Sparkle 2.9.2 for automatic updates of the directly distributed
macOS application. The initial distribution will remain unsigned and
unnotarized because the maintainer does not currently have an Apple Developer
account. Sparkle's Ed25519 signatures and HTTPS transport will protect update
integrity, but they do not remove macOS Gatekeeper warnings from the initial
installation.

This specification supplements the base product specification at
docs/09-12-2026-porto-macos-port-monitor-spec.md. It does not authorize Apple
Developer signing, notarization, App Store distribution, or publication of
credentials.

## 2. Scope

This specification covers:

- Embedding Sparkle 2.9.2 through the XcodeGen Swift Package Manager
  dependency.
- Starting Sparkle from the SwiftUI app lifecycle without adding a main window
  or Dock presence.
- Showing a user-invoked Check for Updates… action in Porto's existing overflow
  menu.
- Enabling scheduled update checks and preserving user control over download
  and installation.
- Publishing a signed Sparkle appcast and update archive through the existing
  tag-triggered GitHub Release workflow.
- Documenting the one-time manual bootstrap required by users already running
  Porto 1.0.1.

It does not cover:

- Apple Developer ID signing, notarization, App Store submission, or paid
  distribution services.
- A custom updater UI, privileged helper, launch daemon, or separate installer
  package.
- Silent forced restarts, automatic SIGKILL, telemetry, anonymous system
  profiling, or feature-flag delivery of native code.
- Delta updates in the first Sparkle release. The workflow may publish one full
  universal ZIP per release.

## 3. Runtime behavior

- Porto continues to use SwiftUI MenuBarExtra with
  .menuBarExtraStyle(.window) and LSUIElement=true.
- The updater is created once by PortoApp and is retained for the lifetime of
  the application.
- Release builds start Sparkle's updater automatically. Debug builds do not
  start the updater or contact the production appcast.
- SUEnableAutomaticChecks is true so users are not required to approve a
  second-launch permission prompt before scheduled checks begin.
- SUScheduledCheckInterval is 86400 seconds (one day).
- SUAutomaticallyUpdate is false. Porto may check automatically, but the
  standard Sparkle UI must ask the user before downloading and installing an
  update by default.
- The overflow menu contains Check for Updates…. The item is disabled while
  Sparkle reports that a check cannot be started.
- The standard Sparkle user driver supplies update progress, release notes,
  download, installation, and relaunch behavior. Porto will not replace it
  with custom panels in this scope.
- Sparkle system profiling remains disabled. Porto sends no telemetry.

## 4. Feed and archive contract

The application Info.plist contains:

- SUFeedURL set to
  https://github.com/wehyn/porto/releases/latest/download/appcast.xml.
- SUPublicEDKey set to the base64 public key generated by Sparkle's
  generate_keys tool.
- SURequireSignedFeed=true.
- SUVerifyUpdateBeforeExtraction=true.
- SUEnableAutomaticChecks=true.
- SUScheduledCheckInterval=86400.
- SUAutomaticallyUpdate=false.

Each tagged release publishes these assets in the GitHub Release:

- Porto-<MARKETING_VERSION>-macOS-universal.zip, containing only Porto.app.
- The existing SHA-256 checksum for the ZIP.
- appcast.xml, generated by Sparkle and signed with the Ed25519 private key.

The appcast enclosure URL uses the tag-specific HTTPS release path:

https://github.com/wehyn/porto/releases/download/<tag>/Porto-<version>-macOS-universal.zip

The GitHub latest/download/appcast.xml URL is the stable feed URL. The workflow
publishes only the current full archive in its generated appcast for the
initial implementation; delta archives are not required.

## 5. Signing and secret handling

- The Sparkle Ed25519 private key is generated once and backed up offline.
- The private key is stored in the GitHub Actions secret PORTO_SPARKLE_ED_KEY
  and is passed to generate_appcast through standard input using
  --ed-key-file -.
- The private key must never appear in the repository, an Info.plist, a
  release asset, a workflow log, or a committed planning document.
- The public key is safe to embed in the application Info.plist.
- The archive signature is the authenticity check. The SHA-256 file is a
  distribution-integrity convenience and must not be treated as an independent
  publisher identity when it is downloaded from the same release.
- Update and feed URLs must use HTTPS.
- Because no Apple Developer ID signature exists, macOS may still require
  Privacy & Security → Open Anyway for the initial app installation. Sparkle
  must not bypass Gatekeeper or advise users to disable it globally.

## 6. Versioning and bootstrap

project.yml remains the canonical version source. At the current repository
state, the first Sparkle-enabled bridge release is MARKETING_VERSION=1.0.2 and
CURRENT_PROJECT_VERSION=3, published under tag v1.0.2.

Users running the existing unsigned Porto 1.0.1 build must manually download and
replace it with the bridge release once. Porto 1.0.1 has no updater code, so it
cannot discover the bridge release. Every release after the bridge must retain
the same Sparkle public key and feed URL so the installed updater can continue
receiving updates.

The release workflow must fail if the pushed tag does not equal
v<CFBundleShortVersionString> in the built app. Every published build must also
increment CFBundleVersion.

## 7. Acceptance criteria

- XcodeGen generates a project with exactly one new runtime package, Sparkle
  2.9.2, linked to the Porto application target.
- ./scripts/ci.sh passes all tests and the unsigned Debug build.
- Debug Porto does not start an updater or contact the production feed.
- A Release Porto build retains LSUIElement=true, has no WindowGroup or Dock
  entry, and contains the five update behavior keys plus a valid Sparkle public
  key and feed URL.
- The overflow menu exposes an accessible Check for Updates… action without
  changing Settings, About, Quit, refresh, scanning, or process-control
  behavior.
- The appcast helper rejects a missing Sparkle tool, a missing private key on
  standard input, a non-HTTPS download prefix, an absent archive, invalid XML,
  a missing Ed25519 signature, or a missing release entry.
- A tag-triggered workflow builds the universal ZIP, generates a signed appcast,
  verifies the tag/version match, and uploads the ZIP, checksum, and appcast to
  the GitHub Release without Apple credentials.
- A staged two-version update test shows a Sparkle-enabled older build finding
  and installing the newer unsigned ZIP after user confirmation.
- Existing v1.0.1 users are explicitly documented as requiring the one-time
  manual bridge installation.
